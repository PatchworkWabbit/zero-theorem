# V4.7.8 recovery approval and continuation

V4.7.8 closes the handoff between a ready recovery candidate and normal engine
execution. Both fresh whole-body recovery and existing candidate-ready search
checkpoints use the same approval path. An explicit `--resume-candidate` command
also supports a chosen target memory.

## Checks before promotion

- Compatible schema and archive preflight, including existing construction manifests.
- Consecutive foundation states and matching zero identities.
- Exact rational tree values, expression text and leaf metadata.
- Earlier parent references and full re-execution of supported rational construction rules.
- Whole-body saved-task constraints and archive dependency/index audits.
- A matching damaged-source fingerprint and one unambiguous ready candidate for automatic selection.

Before installing approved memory, the engine writes and verifies an exact backup
of the previous target bytes, then uses atomic replacement. The candidate remains
unchanged. Inspection mode never promotes a candidate. Normal engine work resumes
in the same invocation; successful continuation is recorded on the normal save
path, after queue work and coverage checks. Storage failure does not leave an
in-memory successful-continuation flag.

## Reproducible regression results

Run with Python 3 and SymPy 1.14.0:

```bash
python3 -m unittest -v test_zero_body_recovery test_zero_resume
```

All **16 tests passed**: nine existing whole-body recovery tests retargeted to
V4.7.8, plus seven approval/resume tests. Fixtures are generated by the actual
engine; no user memory is required or published. Checks cover actual exploration
and save after promotion, backup preservation, rejection of invalid arithmetic,
foundation and parent metadata, the saved-ready loader, inspection-only behavior,
stale source fingerprints, conflicting candidates, and failed-save bookkeeping.

## Damaged-memory continuation experiment

Using a temporary copy of the supplied corrupted master, fresh whole-body recovery
reconstructed rational records 20, 22, 23, 116 and 117 from surviving evidence,
approved 132 rational expressions, resumed, and saved an archive containing
296 rational records. A separate existing-ready-checkpoint test reached the same
result. A following normal run reached 437 rational records. In both recovery
paths, the backup exactly matched the damaged input bytes.

The user's Android V4.7.8 output also reported:

- Recovery continuation verified and saved at run 2.
- Foundation advanced from [0,1,2,3] through state 6.
- Archive counts: 296 rational, 126 complex, 88 symbolic, 20 calculus, 24 roles.
- Complete zero-core passage coverage across all 554 records.
- Archive link audit: 984 typed dependency links, 1,393 pending tasks inspected,
  and zero structural issues.
- Interactive value queries and the complex discovery index remained available.

## Limits of these results

Approval establishes the documented operational checks, not authenticated
historical restoration. The two quarantined damaged-span records remain marked
unknown; `original_recovery_verified` remains false. An intact-master comparison
is still required to establish exact original-content restoration.

Rational constructions receive exact arithmetic validation; other archives receive
manifest, coverage and structural checks rather than a new independent evaluation
of every mathematical result. Existing manifests detect inconsistency but do not
authenticate against coordinated replacement of data and checksums. General data
repair and arbitrary Python source-code reconstruction are not established by
this experiment. Existing exploration budgets and mathematical rules are retained.
